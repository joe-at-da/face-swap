# E2E Tests in CI — Brainstorm

**Date:** 2026-03-06
**Status:** Ready for planning

## Problem

The current GitHub Actions workflow (`.github/workflows/e2e-tests.yml`) runs E2E tests against Coolify preview deployments, but tests **always fail** because:

1. Tests need **Supabase Admin API** (SERVICE_KEY) to create/delete test users and generate auth links — not exposed via Coolify previews
2. Tests need **Mailpit** to capture OTP emails — not available on Coolify previews
3. `global-setup.ts` has a **localhost safety guard** that refuses non-localhost Supabase URLs
4. No `.env` file in CI — `SUPABASE_URL` is empty, causing immediate failure

## What We're Building

Replace the Coolify-based CI workflow with a Docker Compose approach that spins up the full local dev stack in GitHub Actions, matching the local development environment exactly.

### Core approach

1. Run `setup-worktree.sh` in GitHub Actions to start Docker Compose (Next.js + Supabase + Mailpit)
2. Install Playwright on the host runner
3. Run tests against `localhost` — same as local dev
4. Upload HTML report as artifact + GitHub Pages

### Browser scope

- **CI:** Chromium only (~15 min test execution, ~25 min total job)
- **Local:** All 5 browsers (chromium, firefox, webkit, mobile-chrome, mobile-safari)

### Environment variables

**Auto-generated by `setup-worktree.sh` (no secrets needed):**
- `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `MAILPIT_HTTP_PORT`, `MAILPIT_SMTP_PORT`
- `NEXT_PUBLIC_FRONTEND_URL`, `NEXTJS_PORT`, `KONG_PORT`, `POSTGRES_PORT`
- All `SERVICE_PASSWORD_*` keys (JWT, Postgres, MinIO, etc.)

**GitHub Secrets (manual, for future-proofing):**
- `OPENAI_API_KEY`, `COHERE_API_KEY` — not used by current tests, but needed if future tests exercise AI search
- `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY` — not used by current tests, but needed if future tests exercise payments
- Other external API keys as needed

**Not needed (tests don't touch these features):**
- `RUNPOD_API_KEY` — video processing
- `MAILJET_API_*` — production email sending
- `DO_SPACES_*` — file storage
- `POSTIZ_*` — social media posting

### Routes tested (no external APIs)

Tests only visit: `/signin`, `/signup`, `/dashboard`, `/dashboard/my-clips`, `/dashboard/create-clips`, `/dashboard/settings`, `/setup`, `/mp-setup`, `/team-setup`, `/no-team-access`, `/api/setup/complete`, `/api/setup/profile`

None of these trigger external API calls (OpenAI, Stripe, RunPod, etc.).

## Why This Approach

### Explored and rejected

1. **Coolify preview tests (current)** — Fundamentally broken. No admin API, no Mailpit, localhost guard blocks it.
2. **Coolify env sync** — Could pull envs via Coolify API, but still need local Supabase + Mailpit. Adds complexity (API token, parsing, overrides) for no benefit since tests don't use external API keys.
3. **Supabase CLI (`npx supabase start`)** — Different from local dev environment. Would need separate Mailpit setup. Risk of subtle differences.
4. **Split workflow (smoke on preview + full on merge)** — Full failures caught late. Two workflows to maintain. Need to write a separate smoke suite.
5. **Disable CI tests** — Kicks the can down the road. No automated coverage.

### Why Docker Compose wins

- Same environment as local dev = same test results
- `setup-worktree.sh` already handles everything (ports, secrets, migrations, seeding)
- GitHub Actions `ubuntu-latest` has Docker pre-installed
- No test code changes needed — localhost checks pass, all services available
- ~25 min total job time (acceptable)
- Zero external secrets required today, easy to add later

## Key Decisions

1. **Docker Compose in CI** — not Coolify previews, not Supabase CLI
2. **Chromium only in CI** — cross-browser testing stays local
3. **Drop Coolify wait** — tests run against localhost, Coolify previews deploy independently
4. **GitHub Secrets for API keys** — future-proofing, not needed today
5. **Keep report upload** — artifact + GitHub Pages for PR visibility

## Open Questions

1. **Docker layer caching** — should we cache Docker images between runs to speed up startup?
2. **setup-worktree.sh CI compatibility** — may need minor tweaks (e.g., skip interactive prompts, handle CI-specific paths)
3. **Concurrency** — should parallel PRs share resources or get separate Docker stacks? (setup-worktree.sh uses path-based port hashing, so this should work automatically)
4. **When to trigger** — every PR push, or only on certain conditions (e.g., skip if only docs changed)?
